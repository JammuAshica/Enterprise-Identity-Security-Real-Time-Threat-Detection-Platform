**Report updated:** 19 November 2026

## Executive summary

This project is a synthetic identity-security and security-operations demonstration. It combines a FastAPI service, PostgreSQL persistence, and a React dashboard to manage identities and sessions, collect security events, detect selected suspicious patterns, and support incident triage.

The application is intended for demonstration and coursework, not for production security operations. The impossible-travel workflow is implemented in the simulator and threat engine. Its current PostgreSQL-backed end-to-end demonstration and browser/dashboard verification are **not confirmed in this update** because the Docker CLI is present but no Docker daemon or local PostgreSQL service is available in the execution environment.

## Goals and capabilities

- Authenticate seeded users with JWT access and refresh tokens and support session revocation.
- Apply role-based permissions to administrator, security analyst, and employee functions.
- Record security events and provide audit-log and live-event views.
- Demonstrate brute-force, impossible-travel, and privilege-escalation detection, along with benign synthetic traffic.
- Generate alerts and incidents for detected scenarios and expose incident assignment, containment, and resolution workflows.

All users, locations, IP addresses, and activity generated by the simulator are synthetic.

## Architecture

| Layer | Implementation |
|---|---|
| Browser application | React 18, Vite, Tailwind CSS |
| API | Python 3.11+, FastAPI, Pydantic, SQLAlchemy |
| Authentication | JWT access/refresh tokens, password hashing, session tracking, and role-based authorization |
| Persistence | PostgreSQL, including in the automated-test configuration |
| Container deployment | Docker Compose, PostgreSQL, FastAPI, and Nginx |

The frontend uses same-origin `/api/v1` requests. Vite proxies these requests in local development and Nginx proxies them in the container deployment. The backend creates its schema and seeds synthetic users at startup.

## Impossible-travel demonstration flow

The simulator creates two successful sign-in events for `sarah_connor`: one in London, followed 20 minutes later by one in Tokyo. The threat engine compares the latest geolocated sign-in with the previous sign-in for that user, calculates great-circle distance and travel speed, and creates a high-severity alert and open incident when the configured speed threshold is exceeded.

After a successful run, the expected evidence is:

1. Both London and Tokyo events in the security-event feed.
2. An `IMPOSSIBLE_TRAVEL` alert for `sarah_connor`, visible in dashboard alerts.
3. An open incident titled for impossible travel, visible in the incident queue and its details pane.

## Demo credentials and exposure review

The four seeded usernames now each use a separate environment variable: `DEMO_ADMIN_PASSWORD`, `DEMO_ANALYST_PASSWORD`, `DEMO_EMPLOYEE_PASSWORD`, and `DEMO_SARAH_PASSWORD`. Application settings reject values shorter than 12 characters, placeholders, and any duplicate among the four configured passwords. Startup hashes each account’s configured password; no demo plaintext password is stored in application source.

`.env.example` contains placeholders only. A private local `.env` was generated for this checkout, is excluded by `.gitignore`, and must never be committed or shared. The test suite also has separate random demo-account settings; its fixed test-user passwords are test fixtures and are not the seeded demo credentials. Never reuse any demo password for a real account or service.

The review found that `john_doe` and `sarah_connor` previously shared the employee password. That reuse has been removed in the configuration, seeding logic, Docker Compose environment, and setup instructions. This review does not certify external forks, repository-hosting caches, collaborators’ clones, or credentials outside this checkout. Rotate any real credential if it was ever exposed.

## Local deployment and demonstration

Prerequisites: Docker Desktop with its engine running. From the repository root, copy `.env.example` to `.env`, replace every placeholder with private unique values, and run:

```powershell
Copy-Item .env.example .env
docker compose up --build
```

The dashboard is served at `http://localhost:8081`; the API health check and docs are at `http://localhost:8000/health` and `http://localhost:8000/docs`. Log in with a locally configured demo account, open the Attack Simulator, and launch **Impossible Travel Anomaly**. Confirm the two events in the live/security feed and confirm the matching alert and incident on the dashboard and incident page.

The `Sarah` account’s password is the value of `DEMO_SARAH_PASSWORD` in the private `.env`; do not put that value in a report or commit.
