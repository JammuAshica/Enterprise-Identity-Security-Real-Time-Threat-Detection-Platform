# Enterprise Identity Security & Real-Time Threat Detection Platform

An identity security platform for managing users and access while monitoring security events, detecting suspicious activity, and coordinating incident response. It includes a FastAPI backend and a React-based security operations dashboard.

## Features

- JWT-based authentication, refresh tokens, and session revocation
- Role-based access control and user administration
- Security event and audit log monitoring
- Threat alerts and incident management
- Threat simulation for testing detection workflows
- API documentation generated by FastAPI

## Tech stack

- **Backend:** Python, FastAPI, SQLAlchemy, Pydantic
- **Database:** PostgreSQL for local development, tests, and Docker Compose deployment.
- **Frontend:** React, Vite, Tailwind CSS
- **Containers:** Docker Compose, PostgreSQL, Nginx

## Requirements

- Python 3.11 or newer
- Node.js and npm

## Run locally

### Backend

PostgreSQL is required. The simplest setup is Docker Compose below. To run the API directly with Python, start a PostgreSQL server and provide a PostgreSQL `DATABASE_URL` plus the demo passwords through environment variables or `backend/.env`.

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python run.py
```

The API is available at `http://localhost:8000`. Interactive API documentation is at `http://localhost:8000/docs`, and the health check is at `http://localhost:8000/health`.

The backend creates its PostgreSQL database schema on startup. Configuration can be supplied through environment variables or a `backend/.env` file. For deployments outside development, set a secure `JWT_SECRET_KEY` (at least 32 characters) and configure `DATABASE_URL`.

### Frontend

In another terminal, change to the `frontend` directory and run:

```powershell
npm install
npm run dev
```

Vite prints the local frontend URL when it starts. The frontend sends API requests to `/api/v1`; the Vite development proxy forwards them to `http://127.0.0.1:8000`.

## Run backend tests

The test configuration reports statement coverage by module and enforces an 80% minimum. Tests require a dedicated PostgreSQL database configured by `TEST_DATABASE_URL`; tests create and drop tables in that database, so never point it at a database containing data you need to keep. Run them using the isolated Compose test profile from the repository root:

```powershell
docker compose --profile test run --build --rm tests
```

The test database uses a separate named volume from the application database. Do not use `docker compose down -v` unless you intend to delete both databases. To run pytest directly, set both `DATABASE_URL` and `TEST_DATABASE_URL` to a dedicated PostgreSQL database before running `python -m pytest` from `backend`.

## Run with Docker Compose (PostgreSQL)

Install Docker Desktop, then from the repository root copy `.env.example` to `.env` and replace every placeholder. Set a PostgreSQL password and JWT secret, plus three distinct demo-account passwords of at least 12 characters each. Use URL-safe letters and digits for the PostgreSQL password because it is embedded in `DATABASE_URL`. Keep `.env` private and do not commit it.

```powershell
Copy-Item .env.example .env
docker compose up --build
```

Open the frontend at `http://localhost:8081`, the API docs at `http://localhost:8000/docs`, and the health check at `http://localhost:8000/health`. Compose waits for PostgreSQL and the backend health check before starting dependent services. The database uses a named volume and persists across container restarts.

To stop the services while retaining database data, press `Ctrl+C` and run `docker compose down`. To remove the local database volume as well, use `docker compose down -v`; this permanently deletes the Compose database.

## Functional demonstration

1. Sign in with a locally seeded demo account using the password you configured in the private environment file. Demo usernames are `admin`, `analyst_jane`, and `john_doe`.
2. Verify role-based access by inspecting the dashboard and user/incident pages. Sign in as the analyst or employee demo role to compare permissions.
3. Use **Attack Simulator** to generate a brute-force, impossible-travel, or privilege-escalation scenario.
4. Review the generated security events, alerts, and incidents in the dashboard and incident pages.
5. Test session management by signing out, signing back in, and using the session list/revocation controls.

The demo accounts and generated activity are synthetic and are not suitable for real accounts or production use. Configure three distinct passwords of at least 12 characters using `DEMO_ADMIN_PASSWORD`, `DEMO_ANALYST_PASSWORD`, and `DEMO_EMPLOYEE_PASSWORD` in the private environment file. Do not commit that file.

## Repository exposure check

Before publishing or submitting, inspect tracked files and the complete Git history for accidental secrets and confidential material. `.env` and local database files are ignored, but ignore rules do not remove files already committed or present in Git history. The `main` history was rewritten to remove the former synthetic demo passwords and use the GitHub account identity for commit attribution. Existing clones, forks, and hosting caches may retain old commit objects. Rotate any real credentials that may have been exposed. A local scan cannot certify that all GitHub history, forks, or repository settings are free of confidential information.
